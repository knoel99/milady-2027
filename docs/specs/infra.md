# Infrastructure contract — HPC / cloud computing for MilaDy

Goal: a user can **clone the repository and deploy with a single command** on (1) a GPU VM rented in the cloud, (2) a Slurm HPC cluster (IDRIS Jean Zay, mesocentres, cloud Slurm), (3) a laptop (CPU), then launch the simulation, training and evaluation campaigns of the internship and the thesis, with data in a standard format and a central catalog of results.

Root: the `milady-2027/` folder (root of the `knoel99/milady-2027` repository). Everything below is relative to this root.

## 2. MilaDy data format ("MFF", version 1.0)

Principle: **compatible with The Well's HDF5 format** (Ohana et al., NeurIPS 2024 Datasets & Benchmarks; repository PolymathicAI/the_well, "data format" page to be read and followed exactly) for regular grids, plus **MilaDy metadata** in attributes prefixed `milady_`. One file = one simulation (one or more trajectories with the same parameters).

- The Well groups and attributes: root attributes (`dataset_name`, `grid_type`, `n_spatial_dims`, `n_trajectories`, `simulation_parameters` + one attribute per parameter), groups `dimensions/` (`time`, `x`, `y`, `z`), `boundary_conditions/`, `scalars/`, `t0_fields/` (scalars), `t1_fields/` (vectors), `t2_fields/` (tensors), with their attributes (`field_names`, `dim_varying`, `sample_varying`, `time_varying`…). Shape of a vector field: `(n_trajectories, n_t, nx, ny, nz, 3)`.
- Standard MilaDy fields: `t1_fields/velocity` (**u**), `t1_fields/magnetic_field` (**B**, Alfvén units); optional `t1_fields/vector_potential` (**A**), `t0_fields/pressure`.
- MilaDy attributes (root): `milady_format_version` = "1.0", `milady_code` (`mhd3d_torch`, `mhd2d_numpy`, `sfemans`, `latu`…), `milady_code_version`, `milady_git_commit`, `milady_parameters` (JSON: Re, Rm, Pm, mu_r, forcing…), `milady_nondimensionalization` (text), `milady_created`, `milady_host`, `milady_command`, `milady_uuid` (= identifier in the catalog).
- Optional group `milady_spectral/`: Fourier coefficients (rfftn) of the fields, for periodic domains (exact derivatives, more compact).
- Optional group `milady_diagnostics/`: time series (kinetic and magnetic energy, dissipation, injection, helicities, max |∇·B|).
- Storage: float32, chunked by time step (`chunks=(1, 1, *spatial, comp)`), `gzip` compression level 4 (or `lzf`); SHA-256 checksum computed at write time and stored in the catalog.
- Extension `grid_type = "fourier_fe_axisym"` (SFEMaNS): meridian nodes (r, z), connectivity, azimuthal modes m, cos/sin coefficients per mode, without interpolation; interpolation tool to a regular cylindrical or Cartesian grid for learning. Writing, validation and interpolation are implemented; only the reader of native SFEMaNS files is a skeleton (SFEMaNS data are not public).
- Cloud variant: the same hierarchy in **Zarr** (chunked reading from S3), through the same API.
- `milady.data.format.validate(path)` checks conformity (groups, shapes, attributes, JSON schema of the metadata).

## 3. Catalog (PostgreSQL; SQLite in portable mode)

Tables (UUID keys, UTC timestamps, JSONB for parameters):
- `campaign` (id, name, description, config_yaml, created_at)
- `simulation` (id, campaign_id, code, code_version, git_commit, parameters JSONB, grid JSONB, status ∈ {queued, running, done, failed}, host, n_gpus, n_cpus, wall_time_s, started_at, finished_at, notes)
- `file` (id, simulation_id, kind ∈ {fields, spectral, diagnostics, checkpoint, log}, uri, format_version, size_bytes, sha256, n_t, t_start, t_end, created_at)
- `diagnostic` (simulation_id, name, t, value) — lightweight time series for fast queries
- `dataset` (id, name, version, description, created_at) + `dataset_member` (dataset_id, file_id, split ∈ {train, val, test})
- `model` (id, name, architecture, constraint_mechanism, hyperparams JSONB, dataset_id, mlflow_run_id, checkpoint_uri, git_commit, created_at)
- `evaluation` (id, model_id, parameters JSONB, metric, value, n_samples, seed, details JSONB, created_at)
- `job` (id, kind, scheduler ∈ {local, docker, slurm}, external_id, simulation_id or model_id, status, submitted_at, started_at, finished_at, log_uri)
- view `v_eval_summary` (mean and standard deviation per model, metric and parameters).

MLflow (same PostgreSQL, separate database; artifacts in S3) tracks the training runs; `model.mlflow_run_id` links the two.

## 4. Storage

- Heavy objects (MFF files, checkpoints, figures): **S3** — MinIO in the compose file (buckets `milady-data`, `milady-models`, `mlflow`), or a provider bucket (AWS S3, Scaleway, OVHcloud) by changing `MILADY_STORAGE_URI` and the credentials.
- On HPC: `$SCRATCH` / `$WORK` paths (local files), SQLite catalog on `$WORK` or a reachable remote PostgreSQL.
- URI convention: `{MILADY_STORAGE_URI}/{campaign}/{simulation_uuid}/fields.h5` (optional Zarr copy `fields.zarr`, final checkpoint `checkpoint.npz`).

## 5. Deployment

- **Cloud GPU VM**: `git clone … && cd milady-2027 && sudo infra/deploy/bootstrap_vm.sh`; installs Docker and the NVIDIA Container Toolkit if a GPU is detected, generates `.env` (random passwords), builds the image (`Dockerfile.gpu` if GPU), starts `db`, `s3`, `mlflow`, then `make smoke` (tiny 3D simulation → MFF file → catalog → one-iteration training → evaluation).
- **Slurm HPC**: `make sif` (Apptainer from the Docker image or `apptainer.def`), then `python -m milady.sweep infra/configs/stage2_abc3d.yaml --scheduler slurm` (job array), `sbatch infra/slurm/train.sbatch infra/configs/train_fm3d.yaml`. Notes for Jean Zay (modules, GPU partitions, `$WORK`, `$SCRATCH`, no Internet on compute nodes).
- **Laptop**: `make setup` (venv + `pip install -e .`), SQLite catalog, local storage `./data`.
- No secret in the repository; `.env` and credentials are in `.gitignore`.

## 6. 3D solver and training (stage 2 of the thesis)

- `src/milady/sim/mhd3d.py`: periodic pseudo-spectral 3D incompressible MHD (PyTorch, `torch.fft`, CPU/GPU, float32/float64), 2/3 dealiasing, integrating-factor RK4; imposed flow (kinematic, ABC or Taylor–Green) or full forced dynamics (ABC or Taylor–Green forcing); ∇·u = ∇·B = 0 preserved by projection; diagnostics (energies, dissipation, injection, helicities, max |∇·B|). Tests: energy balance, divergence at machine precision, reproduction of the ABC kinematic threshold (≈ 8.9) at low resolution.
- `src/milady/train/fm3d.py`: flow matching conditioned on (Rm, Re…); vector-potential representation in the truncated Fourier basis (exact zero divergence, Coulomb gauge k·Â = 0); optional stationarity loss (unbiased estimator with two half-batches); optional B → −B symmetry; `torchrun` / DDP; MLflow logging; checkpoints to S3.
- `src/milady/eval/metrics.py`: relative divergence, spectra E_u(k) and E_B(k), helicities, balance residuals, energy distance between laws.
